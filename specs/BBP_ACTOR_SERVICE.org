* 1. Authority

Current source and tests are authoritative. The document contract is StarIntel 0.9 and current =starintel-server= source defines durable routing and at-least-once delivery.

RabbitMQ connections and channels are owned by exactly one consumer or publisher thread. Cross-thread broker operations are scheduled with =add_callback_threadsafe= or sent as actor messages.

* 2. Document and routing contracts

=bbp.document_boundary= owns parsing, canonical field access, construction, serialization, and validation.

| Operation | Routing key |
|-----------+-------------|
| external target delivery | =actors.<actor>.new.target= |
| durable new finding | =documents.ingest.<dtype>= |
| persisted-document event | =documents.new.<dtype>= |
| update ingest | =documents.updated.<dtype>= |
| actor event | =event.<eventType>= |

All required document and relation messages are persistent UTF-8 JSON with AMQP =type= equal to canonical =dtype=.

* 3. Publisher settlement

** 3.1 Worker ownership

Each =PublisherWorker= owns one private =BlockingConnection= and one private channel. The channel enables =confirm_delivery()= before publishing.

Every publish uses =mandatory=True=.

** 3.2 Settlement result

=PublishResult= contains:

- success/failure;
- routing key;
- number of attempts;
- failure category (=transient= or =permanent=);
- bounded error text.

Required documents and relations use synchronous Pykka =ask()=. Tool actors never access publisher connections or channels.

** 3.3 Failure classification

Permanent:

- serialization failure;
- invalid publisher message;
- RabbitMQ mandatory return / unroutable routing key.

Transient:

- broker NACK;
- AMQP connection/channel failure;
- publisher actor settlement timeout;
- tool timeout or non-zero exit under the current retry policy;
- unexpected scan processing failure.

Publisher workers retry transient broker failures with configured bounded backoff. They do not retry unroutable messages.

** 3.4 Events

Scan-start, scan-finished, scan-error, and publish-error events are explicitly best-effort. Required output settlement never depends on event delivery.

* 4. Target delivery settlement

Each scan receives a unique =run_id=. Every required output carries that run ID to the publisher message.

A target is ACKed only after:

1. the tool process reaches the configured terminal state;
2. every required document publish is broker-confirmed;
3. every required relation publish is broker-confirmed;
4. the terminal event is emitted under the documented best-effort policy.

Delivery decisions:

| Condition | Decision |
|-----------+----------|
| successful complete settlement | ACK |
| invalid input/schema/actor | emit parse event, ACK |
| transient first failure | NACK, requeue |
| transient redelivery failure | NACK, do not requeue |
| permanent/unroutable required output | NACK, do not requeue |

The =redelivered= flag implements a maximum of two deliveries without changing existing queue arguments. Issue #5 makes retry outputs deterministic.

* 5. DNS settlement

The DNS resolver validates =documents.new.domain=, resolves the document, publishes =documents.updated.domain= through the same required settlement path, and ACKs only after confirmation.

Invalid domain input is ACKed after a categorized parse event. Transient update failure follows the same one-requeue policy as tool targets.

* 6. Shutdown

Shutdown is mailbox-driven and has no fixed sleeps.

1. target consumers receive =StopIntake= and stop RabbitMQ intake while remaining alive;
2. DNS settlement completes and its actor stops;
3. tool pools drain current and queued scans;
4. consumer actors drain ACK/NACK messages and stop;
5. publisher workers drain queued events and stop;
6. RabbitMQ connections close.

Every blocking stop is bounded by =shutdown_timeout_sec=.

* 7. Configuration

Required settlement controls:

- =publisher_max_retries=
- =publisher_retry_delays_sec=
- =publish_settlement_timeout_sec=
- =shutdown_timeout_sec=
- per-tool =publish_timeout_sec=
- DNS =publish_timeout_sec=

Configuration rejects non-positive retry counts/timeouts and negative retry delays.
